第三阶段：实现真正的分块上传和断点续传

目前上传失败后点击重试会重新上传整个文件，需要改为真正的断点续传。

3.1 上传架构

实现统一的底层分块上传服务，普通图片、批量图片和 ZIP/7z 使用同一套上传机制。

建议默认每块 5MiB，允许根据服务器环境调整。

每个上传会话必须有：

* 唯一 upload_id。
* 用户 ID。
* 客户端稳定 upload identity。
* 原始文件名。
* 文件大小。
* MIME 类型。
* SHA-256。
* 总分块数。
* 已成功接收的分块编号。
* 当前状态。
* 创建时间。
* 最后活动时间。
* 过期时间。
* 最终文件 URI。
* 关联导入任务 ID。

服务端需要持久化分块状态，不能只依赖浏览器内存。

3.2 分块上传接口

实现或调整必要的接口：

* 创建上传会话。
* 查询上传会话。
* 上传指定分块。
* 查询已接收分块。
* 恢复上传。
* 合并文件。
* 取消上传。
* 清理过期会话。

接口命名以现有项目路由规范为准，不要为了符合上述名称而重复创建接口。

每个分块必须进行：

* 用户身份验证。
* 权限验证。
* CSRF 验证。
* 分块编号校验。
* 分块大小校验。
* 文件总大小校验。
* 分块完整性校验。
* 重复分块幂等处理。

同一个分块重复提交时，不能重复写入，也不能导致文件损坏。

3.3 断点续传行为

必须支持：

1. 上传中网络断开。
2. HTTP 500。
3. 页面刷新。
4. 浏览器关闭后重新打开页面。
5. 用户重新登录后恢复自己尚未过期的上传任务。
6. 上传过程中某个分块失败。
7. 服务端已经收到分块，但客户端没有收到响应。
8. 文件合并过程中失败。
9. 文件合并完成但任务状态更新失败。

恢复时先查询服务端已接收分块，只上传缺失分块。

不能在重试时重新上传整个文件。

浏览器端可以使用 IndexedDB 保存必要的恢复信息，但服务端状态必须是最终依据。

浏览器本地文件句柄无法恢复时，应提示用户重新选择原文件，并通过文件大小、SHA-256 和上传会话核对是否匹配。不能假装已经获得原文件。

3.4 上传安全

* 分块文件放在受保护的临时目录。
* 临时文件不能被公开访问。
* 防止路径穿越。
* 防止任意文件覆盖。
* 防止不同用户访问彼此上传会话。
* 限制文件大小、分块大小和并发数。
* 对过期会话和孤立分块进行安全清理。
* 合并时使用流式读写，避免将整个大文件加载进 PHP 内存。
* 合并完成后计算最终 SHA-256。
* 校验最终大小和哈希。
* 合并失败时保留必要恢复数据。

不能因为用户刷新页面就清理尚未完成的分块。

第四阶段：修复重复上传记录和队列状态

目前存在一个明确问题：

用户只选择一次 gachig129.zip，界面却出现两条相同名称和大小的记录：

* 一条 pending，服务器确认 0B。
* 另一条 uploading，服务器确认约 10MiB。

这可能是前端重复创建上传记录，也可能是服务端会话恢复时将本地记录和服务端记录重复合并。

必须定位真正原因。

4.1 前端重复事件

检查：

* input change 是否重复绑定。
* 拖拽事件是否重复触发。
* 页面初始化是否执行多次。
* AJAX 重试是否重复创建任务。
* 页面恢复是否重复加入队列。
* 同一文件是否被多个事件重复加入。
* 上传组件销毁和重新初始化。
* 多个脚本是否同时管理上传队列。

4.2 稳定上传身份

建立稳定的客户端上传身份。

要求：

* 同一次选择和恢复流程只有一个活动上传记录。
* 同一文件的重试使用原 upload_id。
* 重复创建会话请求返回已有有效会话。
* 服务端也必须进行幂等控制，不能只靠前端防重复。
* 不同用户主动上传不能相互覆盖。
* 用户主动发起两次上传应保留两个独立业务操作，即使文件内容相同也不能简单认定为同一个上传行为。

不能仅用文件名和大小判断是否是同一次上传。

4.3 状态机

建立清晰的状态流转：

* pending：等待上传。
* queued：排队等待处理。
* uploading：正在上传。
* uploaded：上传完成。
* merging：正在合并文件。
* validating：正在校验。
* processing：正在处理。
* extracting：正在解压。
* importing：正在导入。
* retrying：正在重试。
* paused：已暂停。
* completed：已完成。
* duplicate：文件已存在，已复用。
* skipped：已跳过。
* failed：失败。
* cancelled：已取消。
* interrupted：上传中断。
* review：待审核。

状态流转必须合法、可追踪、幂等。

不能出现一个文件同时拥有两条互相矛盾的活动记录。

不能简单删除前端显示为 pending 的记录。必须确认它对应的服务端会话、分块和请求是否真实存在。

4.4 与现有导入队列协同

优先复用已有 ImageImportWorker、ImportProcessor、TaskRepository 和现有队列。

不要再建立第二套独立的图片导入队列。

上传和导入必须分开管理：

* 上传完成不等于图片导入完成。
* 文件合并完成不等于图片优化完成。
* 图片优化完成不等于内容发布。
* 待审核内容必须保留原有审核流程。

保持原有会员投稿审核规则。

第五阶段：实现全站 SHA-256 精确去重

这是本次任务的重点。

用户希望同一份图片或文件在全站只保存一份物理文件，重复上传时直接复用，而不是重复传输和重复占用 R2 空间。

必须实现真正的服务端精确去重，不允许只在前端显示“重复”。

5.1 统一文件指纹服务

建立统一 SHA-256 文件指纹服务。

先检查项目是否已有可复用的哈希、重复文件检测和文件引用服务。

如果已有，优先扩展现有实现。

如果需要新增索引，必须考虑数据库唯一性约束、并发和数据迁移兼容。

指纹识别不能依赖：

* 文件名。
* 文件扩展名。
* 文件大小。
* 修改时间。
* 文件 URI。

SHA-256 才是精确文件内容判断依据。

文件大小可以作为前置过滤条件，但不能代替哈希校验。

5.2 普通图片上传去重

普通图片、快速发布和批量图片上传全部接入。

推荐流程：

1. 浏览器读取文件并计算 SHA-256。
2. 向服务端查询是否存在相同文件。
3. 服务端检查现有文件实体和实际存储对象。
4. 如果存在健康的相同文件，返回可复用结果。
5. 如果不存在，进入分块上传。
6. 上传完成后服务端再次计算 SHA-256。
7. 进行最终并发去重检查。
8. 只有确认不存在时才真正创建新的物理文件。

客户端计算失败、浏览器不支持或查询失败时，安全回退到正常上传。

服务端必须再次验证，不能信任客户端传来的 SHA-256。

5.3 ZIP/7z 压缩包去重

压缩包本身也需要 SHA-256。

如果完全相同的压缩包已经成功导入：

* 不重复上传文件内容。
* 不重复解压。
* 不重复创建导入任务。
* 显示已有导入记录。
* 显示原任务的成功、失败、跳过数量。
* 提供查看原任务的入口。

如果之前的导入任务失败或只处理了一部分：

* 识别原任务状态。
* 优先恢复原任务。
* 不重复创建第二个任务。
* 不重复创建已经成功导入的内容。

如果用户确实希望重新导入，必须明确确认，并执行有幂等保护的重新导入策略。

不能仅凭文件名相同认定压缩包相同。

5.4 ZIP/7z 内部图片去重

每张解压图片都需要计算 SHA-256。

检查：

1. 同一个压缩包内部是否存在重复图片。
2. 是否在以前其他压缩包中导入过。
3. 是否已经存在于普通图片上传中。
4. 是否已经存在于快速发布上传中。
5. 是否已经存在于 Drupal 文件资产中心。
6. 对应文件实体和物理对象是否健康。

精确重复时：

* 不重复写入 R2。
* 不重复创建物理文件。
* 复用已有 Drupal File Entity。
* 根据业务需求创建新的 Media Entity 和内容记录。
* 记录原始文件名、SHA-256、来源压缩包、复用的文件实体 ID。
* 统计新增、复用、跳过和失败数量。

不能因为图片重复，就直接丢弃用户的第二条投稿。

5.5 文件实体和内容实体必须分开

必须遵守：

物理文件去重，不代表内容记录去重。

例如两个会员分别投稿了相同图片：

* 可以共享同一个物理文件。
* 可以复用同一个 Drupal File Entity。
* 但仍需要分别创建各自的内容记录。
* 各自保留标题、ALT、分类、标签、作者、审核状态、发布日期等信息。
* 不得把第二个会员的投稿直接删除。
* 不得将两个不同内容错误合并。

还需要检查 Drupal File Entity 的引用计数和引用关系。

不能因为一个内容取消发布或删除，就删除其他内容仍在使用的文件。

5.6 R2 对象完整性

当前生产环境使用 Cloudflare R2，CDN 为 https://cdn.gitxx.xyz。

必须兼容当前 R2 存储实现和 URI 映射。

复用前不能只检查数据库中是否存在 File Entity。

必须检查：

* File Entity 是否有效。
* URI 是否有效。
* 真实对象是否存在。
* 对象大小是否匹配。
* 可获得的完整性信息是否匹配。
* 当前存储模式是否能够正确读取。
* 公开文件与私有文件的访问边界是否保持正确。

如果数据库有记录但 R2 对象不存在：

* 不得直接判定为重复并跳过。
* 应进入恢复、重新上传或修复流程。
* 记录错误原因。

不能通过修改 R2 配置来绕过去重问题。

5.7 并发去重

必须防止两个用户同时上传相同文件时，产生两个物理对象。

需要通过数据库唯一约束、锁或其他可靠的并发控制保证：

* 相同 SHA-256 不会同时创建多份物理文件。
* 失败事务能够恢复。
* 对象写入成功但数据库写入失败时能够处理。
* 不会覆盖已有文件。
* 不会误删其他内容引用的文件。

5.8 精确去重与视觉相似图片区分

本次必须完成 SHA-256 精确去重。

同一张图片经过不同压缩、尺寸变化或格式转换后，SHA-256 不同。

这类图片只能作为后续视觉相似检测的候选，不能自动当作完全重复文件删除或跳过。

本次不要为了视觉去重引入不必要的重型依赖，也不要影响现有 WebP 优化流程。

* 总大小。
* 剩余大小。
* 上传速度。
* 上传进度。

* 重复文件详情。

* 手机端展示。

底层数据库、接口计算、文件校验、哈希、大小限制和队列计算仍然使用整数 bytes。

不允许出现同一页面有的显示 MB、有的显示 MiB、有的直接显示字节的情况。
