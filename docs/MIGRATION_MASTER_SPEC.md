XEDC Drupal 自动备份、异地存储、跨服务器迁移与灾难恢复系统

MASTER SPECIFICATION — 完整开发总规范

一、项目目标

为 XEDC Drupal 网站开发一套生产级、可长期维护、可自动化运行的完整备份和灾难恢复系统。

当前生产网站：

* 网站：https://gitxx.xyz
* 项目目录：/var/www/drupal
* Drupal Web 根目录：/var/www/drupal/web
* GitHub 仓库：xxedc/drupal
* 主要运行环境：Ubuntu Linux、Nginx、PHP-FPM、MariaDB、Drupal 11。
* 当前运行版本必须通过实际审计确认，不得直接相信历史记录或假设。

本项目必须实现：

1. 自动发现当前 Drupal 运行环境。
2. 完整备份 Drupal 代码、数据库、文件和必要配置。
3. 自动发现并记录第三方软件及运行依赖。
4. 本地备份和 Cloudflare R2/S3 异地备份。
5. 备份加密、完整性校验、版本清单和恢复 Manifest。
6. 在全新服务器自动安装所需运行环境。
7. 自动恢复 Drupal 数据库、代码、文件和必要配置。
8. 支持更换服务器和更换域名。
9. 支持 SSL 证书部署、验证和自动续期配置。
10. 支持凭据安全恢复和管理员应急恢复。
11. 支持自动化测试、故障修复、回滚和断点续跑。
12. 最终将经过验收的程序和文档提交到 GitHub。
13. 提供中文快速恢复手册，使用户在原服务器损坏时可以按照文档快速恢复网站。

最终验收以真实的全新服务器恢复成功为核心，而不是以代码编写完成为标准。

二、最高优先级：生产环境保护

2.1 当前生产环境绝对保护

当前网站正在运行。生产环境属于只读保护对象。

以下内容未经用户明确授权，绝对禁止修改：

* Drupal 核心。
* Drupal Contrib 模块。
* 自定义模块和主题。
* 生产网站业务代码和功能。
* /var/www/drupal/web 中的生产文件。
* /var/www/drupal/config/sync。
* settings.php。
* 生产数据库及其数据、结构、用户和权限。
* public files 和 private files。
* Nginx 生产配置。
* PHP 和 PHP-FPM 生产配置。
* MariaDB、MySQL、Redis 等生产服务配置。
* 生产 Docker 容器、Compose 项目、网络和卷。
* systemd 服务。
* cron 和生产定时任务。
* Cloudflare DNS、CDN、缓存、安全规则和 SSL。
* 生产 R2/S3 对象及其现有数据。
* /root/backup.sh 旧备份脚本。
* 其他网站、VPN、代理、SSH 和无关服务。

禁止：

* 删除、覆盖、移动生产文件。
* 执行生产数据库迁移。
* 在生产环境执行可能改变网站状态的 Drush 命令。
* 安装、升级、卸载生产软件。
* 修改生产服务配置。
* 重启生产服务。
* 修改现有备份脚本。
* 自动修改 Cloudflare。
* 清理生产磁盘或删除历史文件。
* 使用破坏性 Git 命令清理用户工作。

生产环境只允许必要的只读审计、版本采集、配置读取、文件清单采集，以及经过资源评估的受控备份导出。

数据库导出和文件读取必须评估 CPU、内存、磁盘和 IO 影响。备份任务应采用低优先级、合理并发、超时和限速，不能影响网站正常服务。

2.2 开发和测试隔离

所有新程序的安装、执行、升级、数据库导入、Drupal 恢复、域名迁移和 SSL 测试必须在隔离环境中完成。

推荐顺序：

1. 独立测试 VPS。
2. 独立虚拟机。
3. 严格隔离的 Docker 测试环境。

如果使用 Docker：

* 使用独立 Compose project。
* 使用独立容器名。
* 使用独立网络。
* 使用独立端口。
* 使用独立卷。
* 不得挂载生产 Drupal 目录为可写目录。
* 不得挂载生产数据库目录。
* 不得连接生产数据库。
* 不得使用生产 Redis。
* 不得复用生产 Docker Compose 项目。
* 不得覆盖生产端口。
* 不得使用特权容器。
* 不得挂载 Docker socket。
* 不得连接生产网络。
* 测试 SMTP 必须使用 Mailpit 等邮件接收器。
* 测试凭据必须与生产凭据隔离。
* 测试数据必须脱敏或使用合成数据。

Docker 并不天然保证宿主机安全。必须实际审查卷挂载、网络、权限、端口和宿主机访问能力。

如果当前生产服务器无法提供足够隔离条件，应先使用独立测试 VPS，不得为了方便而冒险。

7.3 加密

2026-11-03 修订，工具 2.3.0 起执行：

* 新的 `xedc-backup` 不生成、也不要求用户保存 `primary.key`、`key_id` 或 `key_b64`。
* 新备份不做客户端加密。本地备份用目录 `0700`、文件 `0600`、服务器访问控制和磁盘安全保护。
* R2 使用私有桶、HTTPS 和服务端静态加密。文档和输出不得把它写成端到端加密。
* R2 凭据只用于访问桶，与备份内容的 SHA256、Manifest 校验分开。
* 2026-11-03 之前的 AES-256-GCM 备份继续兼容。恢复这种旧包时仍要求原来的 `primary.key`。
* 日志脱敏。
* 校验和验证。本地和 R2 上的同一份新备份必须有相同编号、Manifest、SHA256、Drupal 版本、Git 提交以及数据库和文件清单。
* 不得在远程上传和下载校验完成前删除唯一的本地或临时备份。上传中断不得损坏已有完整备份。

增量备份必须具备完整依赖链验证。如果增量设计不可靠，先交付可靠完整备份，再开发增量能力。
