# SEO 分析页面专项修复

本次只改了开始分析和详情页内容基本信息。没有重做 ALT 优化，没有改评分规则，没有改 `config/sync`，没有调用 DeepSeek，没有改生产内容和生产库结构。生产库端口仍是 3306，`xedc_ai` schema 仍是 10002。内容 13 仍是修订 2384、未发布、已撤下，标题仍是「海边风景手机壁纸高清下载」。

## 1. 开始分析缓慢的根因

「开始 SEO 分析」原先在 `SeoSuggestForm::submitForm()` 里同步调用 `ReviewRunner::process()`，并设置 120 秒执行时间。模型请求、本地检查和结果写入都发生在同一次 HTTP 请求中。页面要等这次请求结束才返回。

## 2. 整页刷新的原因

提交使用普通 Form API。处理完成后 `setRedirect()` 跳到详情页，浏览器整页加载新地址。分析进行中的状态不会留在原页面上，所以看起来还要再刷新一次才能看到结果。

## 3. 修改后的异步执行方式

表单改为 Drupal AJAX 提交，不再跳转，也不再在请求里调用模型。

提交时只做这些事：

1. 校验内容 ID 和查看权限。
2. 读取该节点的当前修订版本。
3. 用现有 `ReviewEnqueuer` 写入一条 SEO 分析记录并放入现有队列 `xedc_ai_review`。同一内容已有未完成任务时复用那条记录，不另建一条。
4. 立刻把任务区域替换成「等待处理」。

响应发出之后，`QueueTerminator` 在 `kernel.terminate` 里取走队列中的一项，交给现有 `AiReviewWorker` 执行。生产环境使用 PHP-FPM 时，Symfony 会在 `terminate` 之前调用 `fastcgi_finish_request()`，浏览器不必等模型返回。页面关闭不影响已经开始的这项任务。

页面用轻量状态接口轮询。接口按主键读取一行分析记录，不加载节点。间隔为 2 秒、3 秒、5 秒、8 秒、12 秒，之后保持 15 秒。状态变为已完成、分析失败或已取消后停止。

状态对应关系：

| 记录状态 | 页面 |
| --- | --- |
| pending | 等待处理 |
| processing，本地检查尚未写入 | 正在分析 |
| processing，本地检查已经写入 | 正在生成建议 |
| completed | 已完成 |
| failed | 分析失败 |
| cancelled | 已取消 |

刷新或重新打开列表时，如果当前用户还有未完成的 SEO 任务，表单会恢复这条任务并继续轮询。

## 4. 后台 Worker 实际执行验证

现有队列工人 `xedc_ai_review` 的 cron 时间预算是 120 秒，不是 30 秒。`xedc_ai_cron` 本身不消费这条队列；Drupal 核心 cron 会按插件预算执行它。本次没有把 cron 改成持续循环，也没有引入 Redis。一次页面提交只踢一项，避免低配服务器上并发堆叠。可重试的失败会把队列项放回，留给后续 cron。调用超过 180 秒会被中断并记为失败，不会记成成功。

实验室里把供应商地址指到本机不可达端口，并把密钥文件位置指到一个不存在的路径。生产密钥文件没有读取，也没有改动。Worker 实际 `claimItem` 后执行 `processItem`，在发出 HTTP 请求之前因没有密钥结束。

结果：

- 同一内容连续入队两次，返回同一个任务 ID，队列里只有 1 条。
- Worker 执行后删除了这条队列项。
- 记录状态是 `failed`，错误码是 `no_key`，不是成功。
- 保存的 `revision_id` 是入队时的当前修订。
- `xedc_ai_usage` 行数没有增加，说明没有发出模型请求。
- 浏览器点击后的另一条任务同样是 `failed` / `no_key`，队列再次清空。

浏览器里先看到「等待处理」，随后自动变成「分析失败」，并显示「没有可用密钥 供应商没有可用的 API Key，未调用模型。」地址一直停在 `/admin/xedc/ai/seo`，这次点击只有 1 个 POST，没有整页导航。

完成态的自动更新用实验室记录模拟阶段切换，不调用模型：等待处理 → 正在分析 → 正在生成建议 → 已完成，并出现评分 81 和问题「标题可以更具体」。

## 5. 修订版本 ID 输入框

开始分析表单里的修订版本输入框、类型筛选、标题搜索和预览区已经删除，不是隐藏。表单只保留内容 ID 和「开始 SEO 分析」。

后端用内容 ID 加载节点，取当前修订版本创建任务，并把这个 `revision_id` 写入分析记录。执行时 SEO 任务仍按记录里的修订版本读取，不会偷偷改成更新的修订。历史记录里的 `revision_id` 列和已有数据都没有删除。采纳前的版本冲突检查没有改。

实验室样本只输入内容 ID 1014。记录下来的修订是 2385，与该页面当时的当前修订一致。

## 6. 内容 ID 输入区域

输入区域现在只有：

- 标题：内容 ID
- 占位：请输入内容 ID
- 说明：输入需要进行 SEO 分析的内容 ID，系统将自动读取当前修订版本。

输入框附近不再拼接工作流机器名、审核状态、发布状态或修订号。原先会在输入框下绘制这些信息的脚本已去掉对应输出。详情页的工作流信息仍保留。

## 7. 发布状态读取

发布状态读取当前默认修订的 `isPublished()`，显示「已发布」或「未发布」。

发布时间只读 `field_published_at`。未发布显示「未发布」。已发布但没有这个字段，或字段没有有效时间，显示「暂无发布时间」，不再用修订创建时间代替。

实测：

- 美图 1 已发布，没有发布时间字段，显示「暂无发布时间」和「已发布」。
- 文章 56 已发布，显示真实发布时间 `2026-10-23 23:01`。
- 未发布内容显示「未发布」。

## 8. 工作流中文名称

工作流名称来自内容类型实际关联的 Workflow 配置，读取配置实体的 label。`xedc_editorial` 显示为「DcLili 会员投稿审核」。页面上不再出现 `xedc_editorial`。

内容类型没有关联工作流时显示「未配置」。配置存在但未启用时才显示「未启用」。不会因为分析记录里的工作流字段是空的就显示未启用。

## 9. 工作流状态

工作流状态读取当前修订的 `moderation_state`，再用该工作流的 State 配置取中文 label。

实测：

生产库的默认修订里没有「退回修改」和「已拒绝」的现成内容。这两条是在实验室数据库里新建的文章，按工作流转换得到，容器销毁后不存在。没有修改生产内容的审核状态。

## 10. 历史修订和当前修订

两个编号仍然分开保存和展示。分析记录里的修订不会被改写成当前修订。

美图 13 的历史分析记录仍是修订 2383，当前修订是 2384。详情同时显示这两个数字，并提示「内容已有新修订，本次分析基于历史版本。」当前工作流状态取当前修订；分析修订自己的审核状态单独标成「分析修订审核状态」。两者一致时不重复显示这一行。

## 15. 尚未完成或未验证

- 没有调用 DeepSeek。成功状态的自动刷新是实验室把一条记录按阶段改成完成；真实模型返回的建议文本没有在这次浏览器里生成。

- 实验室使用 PHP 内置服务器。它可能把连接保持到 `terminate` 结束。生产 PHP-FPM 会先结束响应。这次失败发生在联网之前，耗时很短，浏览器仍然先看到「等待处理」。
- 可重试错误的第二次执行依赖现有 cron，本次没有在实验室里跑 cron。
- 生产库默认修订中没有「退回修改」和「已拒绝」。这两项只在实验室新建内容上验证过。
- 详情基本信息把页面类型显示为「页面」。列表筛选里的「基础页」没有改。
