## 十五、Git 检查和 GitHub 推送规则

本次采用有条件推送：

如果发现问题并进行了代码、测试或文档修改，且相关测试全部通过，才提交并推送 GitHub。

具体要求：

1. 开始前记录当前分支和 git status。
2. 保留用户已有未提交修改。
3. 不覆盖其他任务正在进行的修改。
4. 只提交本次审计和修复相关文件。
5. 排除数据库、备份包、日志、临时文件和无关文件。
6. 检查密钥和敏感凭据是否符合当前仓库安全策略。
7. 确认 GitHub 仓库为 Private 后才能推送仓库中已有的敏感恢复密钥。
8. 不允许把 GitHub Deploy Key 私钥放进仓库。
9. 不允许强制推送。
10. 不允许执行 `git reset --hard`。
11. 不允许执行 `git clean -fd`。
12. 不允许删除用户现有修改。
13. 不允许覆盖历史提交。

推送条件：

- 有实际修改：运行相关测试，全部通过后提交并推送 `origin main`。
- 没有任何修改：不创建空提交，不推送。
- 存在 FAIL 或 BLOCKED：先尽可能修复；无法修复则不推送未通过的版本，报告原因。
- 只有文档发生必要修改，也属于实际修改；相关检查通过后可以推送。

推送后必须验证：

- 本地 commit SHA。
- GitHub 远端 commit SHA。
- 两者一致。
- README 已同步到 GitHub。

## 十七、最终执行要求

现在直接开始：

1. 先检查生产网站现状和 Git 工作区。
2. 盘点全部模块、数据、文件和服务。
3. 检查现有备份。
4. 建立独立 Docker 测试环境。
5. 使用真实备份执行完整恢复。
6. 检查恢复后的功能。
7. 发现问题直接修复。
8. 重新执行测试，直到所有可验证项目通过。
9. 更新备份覆盖矩阵和 README。
10. 根据第十五部分的条件决定是否推送 GitHub。

不要只给出一份审计计划。

不要只检查代码而不实际恢复。

不要只运行语法检查就宣布完成。

不要为了测试影响生产网站。

不要为了通过测试删除功能、跳过错误或降低版本要求。

最重要：保护当前网站所有现有内容和功能，在 Docker 中真正测试备份与恢复，发现问题就修复。有修改且测试全部通过才推送 GitHub；没有修改就不推送。
